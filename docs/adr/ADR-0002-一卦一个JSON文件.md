# ADR-0002：一卦一个 JSON 文件而不是数据库

| 项 | 内容 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-10-03 |
| 决策者 | 项目维护者 |
| 影响的模块 | `server/store.mjs`、`core/record.mjs`、`core/migrate.mjs`、`server/index.mjs`、`tools/import.mjs`、`tools/validate.mjs`、`schema/record.schema.json`、`data/records/` |

## 背景

一条卦录落在 `data/records/<id>.json`，id 形如 `202609280338-01`——起卦时间 `YYYYMMDDHHmm` 加两位序号，一经生成不再更改。目录结构由 `server/store.mjs` 的 `Store` 类在构造时 `ensure()` 出来：`records/`、`trash/`、`backups/`，外加 `config.json`。

`Store` 的全部实现是「一个 `Map` 缓存 + 若干文件操作」：

- `loadAll()` 用 `fs.readdirSync` 遍历 `records/`，逐文件 `JSON.parse`，坏文件只 `console.warn` 跳过而不中断启动；
- `list()` 直接在内存里按 `cast.localTime`（缺则 `createdAt`）字符串倒序排；
- `get()`／`has()`／`ids()` 都是 `Map` 操作；
- `save()` 先写 `<id>.json.tmp` 再 `fs.renameSync` 原子替换；
- `remove(id, hard)` 默认把整条记录另存到 `data/trash/<id>-<时间戳>.json` 再删除原件，只有 `hard=true`（HTTP 侧的 `?hard=1`）才真删；
- `stats()` 用几次 `reduce` 现算分类别、吉凶、卦名、体用、复盘状态的分布；
- `backup()` 把 `{ meta, config, records }` 打成一个 JSON 包，`restore(pack, { merge })` 按 id 合并或跳过。

写盘格式是 `JSON.stringify(record, null, 2)`，缩进两格，含中文。`docs/规范.md` 的兼容性承诺里写着：「数据是纯文本 JSON，不依赖本程序也能读。程序跑不起来时，你的卦录依然在。」

`data/` 与程序是分开的：桌面版安装态放 `%APPDATA%\问心卦\data`（卸载不删），命令行版默认用项目里的 `data/`，不可写时回退到同一处用户目录；桌面版还可以通过菜单「数据 → 更换数据目录…」把数据指到别处（例如放进 git 仓库或 OneDrive）。

## 决策

卦录的存储形态**必须**是「一条卦录一个 UTF-8 JSON 文件」，存放在数据目录的 `records/` 下，文件名即 id。**不得**引入数据库、嵌入式 KV 存储或单一大文件归档。删除**必须**先移入 `trash/`，只有用户显式请求彻底删除时才 `hard` 删除。整包备份**必须**是纯文本 JSON。

## 理由

1. **可读、可改、可 git。** 一条卦录的 500 行 JSON 用任何编辑器都能打开；用户可以手改标题、补一段复盘、修一个错字，程序下次启动照读。放进 git 就是一个可 diff 的历史：哪一年改了哪句断语，一眼看得见。
2. **不依赖程序。** 数据库文件需要对应的引擎与驱动才能打开；纯文本 JSON 只要有眼睛就能读。这是「卦录陪几十年」与「程序可能某天跑不起来」这两件事之间唯一的可靠折中。
3. **删改可控。** 文件是用户自己的东西，`rm` 或资源管理器删除是最终手段。程序一侧把删除做成「先入 `trash/`」，是为了让误删有救；而迁移前先写 `data/backups/pre-migration/<id>-v<旧版本>-<时间戳>.json`，是为了让升级有退路。
4. **全量数据集小到不需要索引。** 卦录是「一事一占」，正常使用一年几十条、十年几百条。整包载入进内存的代价可以忽略，而在内存里过滤、排序、聚合比写 SQL 更直观，也不引入查询语言这一层学习成本。
5. **一处实现，多处复用。** `Store` 是唯一的数据入口：HTTP 服务、`tools/import.mjs`、`tools/validate.mjs`、`agent/tools.mjs`、MCP 服务、插件宿主全部经它读写。没有第二套持久化路径，也就没有「命令行导入的卦录服务看不见」这类同步问题——`maybeRescan()` 就是为这个场景补的：它只做一次 `statSync` 比较 `records/` 目录的修改时间，变了就重扫。这个 bug 在开发中真实出现过，被手工实测抓到。

## 后果

### 正面

- 数据是用户资产而非程序资产：可以用任何编辑器改、用任何脚本处理、用任何备份工具同步。
- 迁移可审计：每一条被迁移的记录都留了原件复印件，`data/backups/pre-migration/` 本身就是一份变更日志。
- 备份与恢复是同一套代码的往返：`backup()` 出的包能被 `restore()` 读回。
- 崩溃面小：写盘用的是临时文件加 `rename`，中途断电不会留下半截 JSON。
- 单条记录可被单独取出、发给别人、离线打开（插件 `html-card.mjs` 导出的单文件 HTML 卡片即是此用法）。

### 负面

- **全量载入。** `loadAll()` 在启动时把全部卦录读进内存，任何一次外部改动都要重扫整个目录。以本项目的数据规模可以接受，但**必须**承认它是用「数据量小」这个前提换来的。
- **没有索引，也没有事务。** 按卦名、类别、吉凶筛选都是内存里线性扫；跨多条记录的原子操作不存在——`restore()` 逐条 `save()`，中途失败会留下部分导入的结果。
- **并发写没有保护。** 两个进程同时写同一条卦录，后写的覆盖先写的（只有同一进程内的 `Map` 缓存保持一致）。这是单机单用户软件，不是多人共享服务。
- **目录就是数据量上限。** 几千条时 `readdirSync` 与逐文件 `JSON.parse` 还能接受；几万条就要重新设计，那时本 ADR 需要被新 ADR 取代。
- **文件名的信息量绑死在 id 上。** id 在生成时用 `stampOf(localTime)` 取起卦时间，若起卦时间填错，id 也跟着错——而 id 一经生成不再更改，只能靠重命名文件手工纠正。

## 备选方案与为何不选

| 方案 | 为什么没选 |
|---|---|
| SQLite（Node 22 起有内置 `node:sqlite`） | 单文件二进制，脱离本程序就难以阅读与手改；且把「数据可 git」变成「数据不可 git」（二进制 diff 无意义）。与本 ADR 的核心诉求直接冲突。 |
| 全部卦录放进一个 `records.json` | 写一次就要重写全量文件，任何一次保存都在放大损坏风险；且多人/多工具同时改时冲突面远大于一条一文件。 |
| JSONL（一行一条）追加写 | 追加成本低，但单条修改需要重写整文件或留墓碑记录，最终会演化成一套自制的日志结构存储——那正是本 ADR 想避免的复杂度。 |
| 纯 Markdown 文件存卦录 | 人读最好，但机器解析要靠约定俗成的标题层级，一旦用户手改格式就会解析失败。JSON 有 `schema/record.schema.json` 与 `core/schema.mjs` 兜底，能明确报错。 |
| 云同步／多端数据库 | 与本项目「单机、无账号、默认不出网」的定位冲突，见 [ADR-0006](./ADR-0006-本地优先默认不出网.md)。 |
