# ADR-0005：卦条 v1 作为稳定导入契约

> **注（2026-10-07）**：本篇「卦条 v1 只描述梅花易数」一条表述的**作用域**已由 [ADR-0015](./ADR-0015-卦条v1扩到两法.md) 取代——卦条现在按「法」分梅花与小六壬两个分支。字段名与别名只增不改、报缺不猜、一处实现多处复用等承诺继续有效。

## 背景

「以后新导入的卦怎么办」曾经没有答案：卦录的 JSON 完整但难手写，DeepSeek 的对话文本好粘但没标准。于是另立了 `core/guaTiao.mjs` 定义的「卦条 v1」——一行一个 `键: 值` 的纯文本，首行 `# 卦条 v1` 可省，多条用单独一行 `---` 分隔。

它的契约面由四张表固定：

- `GUATIAO_VERSION = 1` 与 `HEADER = '# 卦条 v1'`；
- `FIELD_ALIASES`：21 组字段别名（**v3 起增至 25 组**，见 [规范.md](../规范.md) §2.2），例如 `title: ['题','标题','title']`、`localTime: ['时','时间','起卦时间','钟表时间','time','localtime']`、`movingPosition: ['动','动爻','moving']`、`signature: ['签','谶','signature']`；
- `METHOD_NAMES`／`METHOD_LABELS`：起卦法中文名与内部 id 的互转（一数一时辰／两数／年月日时／已知卦象 ↔ `numberAndTime`／`twoNumbers`／`timeOnly`／`manual`）；
- `BOOL_TRUE`／`BOOL_FALSE`：是／否类字段的取值集合。

配套机制有三样：`looksLikeGuaTiao(text)` 用于让导入器**自动分流**（粘贴的文本若像卦条就走卦条解析，否则走 `core/importer.mjs` 的自由文本解析）；`parseGuaTiaoMany(text)` 批量解析；`template()` 吐模板，经 `GET /api/guatiao/template` 与 `node tools/import.mjs --template` 供人照抄。

解析原则写死在 `core/importer.mjs` 的头部注释里：**宁可少认，不可错认**。识别结果带 `missing[]`（缺哪些必填）与 `unknownKeys[]`（认不出的键名，多半是写错了字），缺什么报什么，绝不替用户猜一个年份。必填只有「时」；「已知卦象」法再要「本卦」与「动」；其余起卦法要「数」与「动」（「年月日时」免「动」）。

卦条与另外两条导入路径并存，而不是取代它们：

| 路径 | 形态 | 特点 |
|---|---|---|
| 卦条 v1 | `键: 值` 纯文本 | **保证稳定**的契约；人三十秒能写完、脚本能生成、AI 能照着写 |
| 粘贴对话文本 | 任意闲聊记录 | 方便但不稳定（各家格式不一样）；由 `core/importer.mjs` 的启发式解析识别 |
| JSON 备份包 | `{ meta, config, records }` | 整包迁移与恢复 |

三条路径共用同一套下游：都汇入 `core/record.mjs` 的 `buildRecord()`，也就是说都会经过卦象重算与校勘。

`docs/规范.md` 的兼容性承诺是：「卦条 v1 的**字段名与别名不会删改**，只会新增别名。旧文件永远能读。」

## 决策

「卦条 v1」**必须**作为对外保证稳定的导入契约长期存在。它的字段名与别名**不得**删除或改名，只能新增别名；新增别名的同时**应当**同步更新 `docs/规范.md` 的字段字典与 `schema/gua-tiao.schema.json`。解析器遇到缺项**必须**报缺（写进 `missing`），遇到认不出的键名**必须**单独列出（写进 `unknownKeys`），**不得**猜测补全。界面「导入」页、`tools/import.mjs`、agent 的 `save_gua_tiao` 与 `tools/validate.mjs` **必须**共用这一套解析器，**不得**为某个入口另写一套。

## 理由

1. **三方都能产出。** 手写、脚本生成、AI 代写是三种完全不同的生产方式，卦条对三者同样友好：对人是「一行一个字段」，对脚本是「拼字符串」，对 AI 是「有明确键名的结构化文本」。这是它相对对话文本的核心优势。
2. **有版本、有 schema、有校验器。** 契约不是口头约定：有 `GUATIAO_VERSION`、有 `schema/gua-tiao.schema.json`、有 `node tools/validate.mjs` 与 `POST /api/validate` 可以在线验。用户粘进去就知道能不能入库。
3. **不取代对话文本，因为历史需要它。** 已有的旧卦只存在于聊天记录里，要求用户改写一遍是不现实的。三条路径并存、共用下游，是唯一能同时兼顾「历史可录」与「以后稳定」的安排。
4. **报缺不猜，是唯一诚实的选择。** 猜一个年份会产出一条看起来正常、实际错误的卦录，而卦录是要长期回看的东西；报缺只是多一次询问。`tools/check-web.mjs` 专门断言了「缺年月时报缺而不猜」「无关文字不硬认」。
5. **一处实现，多处复用。** 三个入口共用解析器，行为必然一致；否则用户在网页上认得出的卦条，在命令行里认不出，就会失去对契约的信任。

## 后果

### 正面

- 「以后无论谁给你起卦，都能转成卦条录进来」——包括别的 agent 替你起的卦（用「已知卦象」法忠实保留原卦，互卦、变卦、体用由本程序推算）。
- 契约稳定换来长期可用：旧卦条文件十年后仍能读入，因为别名只增不改。
- 批量导入：一次可贴几十条（`---` 分隔），界面、命令行、agent 三处同构。
- 「法」为「一数一时辰」时还带一处小聪明：若别人给的卦只写「报数、时辰、动爻」而不说取法，`core/divination.mjs` 的 `inferMovingFrom()` 会比对两路取法算出动爻，对得上哪一路就按哪一路还原，从而**忠实复现原卦而不是误记成校勘**。
- 卦条可被独立的脚本与 CI 使用：`node tools/validate.mjs 我的卦条.txt` 只校验不导入。

### 负面

- **多一层格式要维护。** 21 组别名（v3 起 25 组）、四张表、一个 schema、一处规范文档、一套在线校验，都要在改动时同步。`AGENTS.md` 的扩展点速查里专门提醒：加一种新导入格式要同时看 `core/guaTiao.mjs` 与 `core/importer.mjs`，并「认不准就报缺，不许猜」。
- **别名越多，误认风险越大。** 键名匹配是大小写无关的前缀式查表，键名过短（如单字）时容易撞上正文里的普通冒号行；`looksLikeGuaTiao()` 用「至少两个中文键值行且含卦条专属键」来降低误判，但仍不是语法级解析。
- **卦条表达不了全部卦录字段。** `claimed.notes`、`origin`、`revisionCount`、`narrativeHtml` 等结构没有对应键名，只能由程序填充或后续用接口补。它是**导入**契约，不是卦录的完整序列化格式。
- **首行与分隔符是软约定。** `# 卦条 v1` 可省、`---` 是分条依据，若用户原文里本来就有 `---`（例如从 Markdown 里剪的一段），会造成误切分。

## 备选方案与为何不选

| 方案 | 为什么没选 |
|---|---|
| 只支持粘贴对话文本 | 各家格式不一致，规则永远追不完；且无法给脚本和 AI 一个稳定的产出目标。 |
| 只支持卦录 JSON | 完整但难手写：要求用户手打嵌套对象与转义，实际不可行。 |
| 用 YAML / TOML 作为导入格式 | 要自带解析器（零依赖下即自己写一个 YAML 子集），复杂度高于收益；`键: 值` 的纯文本已能满足「一行一个字段」。 |
| 用 CSV | 多行原文（`原文: \|`）与中文长文本在 CSV 里很难处理，可读性也差。 |
| 支持多版本并存（v1／v2 双解析） | 目前没有需要破坏兼容的变更；真有需要时应当**新增 ADR**并保留 v1 解析，而不是现在预先设计双轨。 |
