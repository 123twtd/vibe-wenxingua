# ADR-0003：断语用规则引擎而不是让 LLM 写

| 项 | 内容 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-10-03 |
| 决策者 | 项目维护者 |
| 影响的模块 | `core/verdict.mjs`、`core/divination.mjs`、`core/record.mjs`、`agent/loop.mjs`、`agent/provider.mjs`、`web/api.js`、`tools/check.mjs`、`tools/validate.mjs` |

## 背景

断语由 `core/verdict.mjs` 的 `interpret(chart)` 生成，输入是 `core/divination.mjs` 算出的卦局，输出是一个固定形状的对象：

- `signature`：谶语，总纲四句；
- `tone`：**恰好七段**，顺序固定为 `主` → `互` → `变` → `断` → `宜` → `忌` → `应期`（`key` 依次是 `main`／`hu`／`bian`／`duan`／`yi`／`ji`／`yingqi`）；
- `classical`：古辞佐证（本卦卦辞、象传、动爻爻辞、互卦象传、变卦象传）；
- `plain`：通俗解，含 `oneLine`／`focus`／`why[]`／`how[]`；
- `grade`：吉凶等级；
- `category`、`generatedBy`。

文本全部来自 `core/verdict.mjs` 顶部的常量词库：`RELATION_TONE`（体用生克五类，各三句变体）、`RELATION_PLAIN`、`SIGNATURE`（五类各三句）、`HU_TONE`／`HU_PLAIN`、`BIAN_TONE`／`BIAN_PLAIN`、`YING_QI_POSITION`（六爻对应的时间窗）、`YAO_PLAIN`、`CATEGORY_PLAIN`（八类各自的 `focus`／`good[]`／`bad[]`）、`STATE_ADVICE`／`STATE_RANK`。

变体选择不是随机：`pick(arr, seed)` 用 FNV-1a 散列把 `seed` 折成一个下标，而 `seed` 是 `${ben.fullName}|${hu.fullName}|${bian.fullName}|${moving.position}|${rel}|${question}`——也就是**卦局指纹**。所以同一卦局重算，其文必同。

约束是同时存在的：

1. 用户会把断语读很多遍、跨年份回看，文字必须稳定；
2. 断语里的每个判断都必须在界面上摊开可查（「吉凶权衡」把八项的权重、归一值与说明逐项列出）；
3. `agent/loop.mjs` 的 `SYSTEM_PROMPT` 把「卦象必须由工具算出，你不得自行编造」列为绝对不许违反的一条；
4. 助手页允许接本地 Ollama 的小模型（`qwen2.5:7b` 一类），它们多数不支持 function calling，要靠文本协议降级才能干活。

而真实语料证明了 LLM 在这一处的不可靠：录入的六条历史卦录里，`core/record.mjs` 的 `audit()` 照出两处错误——天泽履那条把体用写反（原述「体卦兑金，用卦乾金」，正法应为体乾、用兑），雷泽归妹那条把互卦写成「山火贲」（正法互卦取「二三四爻为下、三四五爻为上」，应为水火既济）。

## 决策

断语**必须**由 `core/verdict.mjs` 的规则引擎生成，**不得**由语言模型撰写或改写。七段的顺序**必须**保持 `主·互·变·断·宜·忌·应期`，`tools/check.mjs` 与 `tools/validate.mjs` 都验这一条。断语的每一处选词**必须**可追溯到词库常量与卦局字段，**不得**引入随机数。AI 助手**必须**原样引述引擎给出的断语，可以另起一段把它翻成行为指引，但**不得**替换、增删或重写定调本身。

## 理由

1. **可复现。** 卦录是要在几年后回看的东西。「年初看到的断语，年底再看还是那几句」这条承诺，只有确定性生成才能兑现。LLM 同样的提示词在不同时刻、不同版本、不同温度下会给出不同文字，而卦录里存的 `reading` 快照与模型输出并不一致——那就等于每次打开都在悄悄改卦。
2. **可追溯。** 规则引擎的每一个字都能被指到来源：这句来自 `RELATION_TONE.ti_ke_yong` 的第 2 个变体，那句来自 `wang.ti.state` 为「囚」查出的 `STATE_ADVICE`。界面上「吉凶权衡」把八项的权重、归一值、说明一并列出，用户不服就改 `core/scoring` 里的权重或词库，改完对旧卦点「重算断语」。LLM 的判断无法这样摊开。
3. **可校准。** 权重与词库可以被调，而且调完之后能用六条真实卦录回归比对（`tools/check.mjs` 会核对这六条的卦象与记录是否一致）。LLM 的「校准」只能靠改提示词再抽样，抽样结果不可复现，因而不可回归。
4. **不可靠的代价在这里特别大。** 模型会记错卦——上述两处历史错误就是实例。卦名、卦符、爻辞、体用生克、动爻、旺衰这些是可以被引擎精确算出的**事实**，让模型来复述事实，等于主动引入错误，而且错误会以「看起来很专业」的形式出现，用户很难发现。
5. **口径必须收敛到有定义的词。** `SYSTEM_PROMPT` 明令不得使用「运势」「能量」「磁场」这类含糊词，只能用体用、旺衰、应期这些有定义的词。规则引擎的输出天然满足这一条，因为词库里根本没有那些词；让模型自由发挥则要反复纠正。

## 后果

### 正面

- 断语稳定、可复现、可追溯、可校准，且随卦录一起被快照保存（见 [ADR-0004](./ADR-0004-cast是唯一真源.md)）。
- 不依赖任何模型即可产出完整断语——没有 API Key 时助手页只显示配置表单，其余功能（起卦、断语、导卦、走势、复盘）全部可用。
- 输出形状固定，前端与导出器可以直接按 `tone[7]` 渲染，不需要容错解析。
- 文言气质由统一的词库保证，各卦之间不会突然换笔调。
- 自检可断言：七段齐备且顺序正确、无重复标点、`check-web.mjs` 检查页面上有没有 `undefined`／`NaN`／`[object Object]` 漏出。

### 负面

- **文采上限固定，且由维护者决定。** 引擎的文气取决于词库写得好不好，不取决于模型有多强。要让断语更活，办法只有扩词库；扩词库是人工活，且每次扩都要保证不破坏「同卦同文」。
- **组合覆盖是有限的。** 五类生克 × 五类变卦关系 × 六爻位 × 五个旺衰 × 八类所问，能表达的语义空间有边界。生僻组合会落到 `unknown` 分支（如「体用生克未明，姑且平看」），读起来偏平。
- **模板感无法完全消除。** `zh()` 把各段按「。」拼接并去重标点，句式骨架在多卦之间会重复。这是用稳定性换来的。
- **维护成本转移给维护者。** 加一个类别要同时改 `CATEGORIES`、`CATEGORY_PLAIN`、`normalizeCategory` 与 `adviceFor` 里的 `catAdvice` 四处，漏一处就会出现「类别认识但宜忌为空」。
- **不能回答超纲问题。** 用户问「这卦跟去年那卦比如何」，引擎没有跨卦语义，只能靠 agent 层去调 `trend`／`get_record` 拼答案。

## 备选方案与为何不选

| 方案 | 为什么没选 |
|---|---|
| 全部交给 LLM 写，每次起卦现生成 | 违反可复现与可追溯两条底线；且无 Key 时程序核心功能即不可用；还会引入「同一卦每次说法都不同」的问题。 |
| 规则引擎出骨架、LLM 润色文字 | 润色即改判。措辞变化会引入原断语没有的倾向（把「宜速不宜久」润成「尽快行动以免错过」就加了紧迫感），而用户读的是润色后的版本，可追溯性也随之消失。 |
| 预先生成全部组合的文本，运行时查表 | 组合数（含所问类别与卦名）远超可维护的文本量；且卦名与卦辞是数据不是模板，无法预生成到有意义的质量。 |
| 用 LLM 校验规则引擎的输出 | 校验者本身不可复现，等于把不确定性引回来；校验规则（七段顺序、无重复标点、动爻阴阳一致）用断言做更便宜也更可靠。 |
| 让模型选词库变体（同一模板不同措辞） | 变体的选择落进 `reading.signature`／`tone` 的快照里会随模型版本漂移。用卦局指纹选变体可以做到「同卦同文」，且完全不依赖网络。 |
