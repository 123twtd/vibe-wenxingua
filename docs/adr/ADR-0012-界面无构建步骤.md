# ADR-0012：界面不做构建步骤（原生 ES 模块）

| 项 | 内容 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-10-03 |
| 决策者 | 项目维护者 |
| 影响的模块 | `web/index.html`、`web/app.js`、`web/views.js`、`web/api.js`、`web/chart.js`、`web/md.js`、`web/palette.js`、`web/style.css`、`server/index.mjs` 的静态服务、`desktop/main.mjs`、`tools/check-web.mjs`、`tools/check-desktop.mjs` |

## 背景

界面直接以原生 ES 模块加载，没有打包、没有转译、没有 npm 前端依赖。入口 `web/index.html` 只有 46 行：一块 `<header>` 顶栏、一块 `<nav id="nav">`、一块 `<main id="main">`、一行 `<div id="meta-line">`、一块 `<footer id="status">`，加一句 `<script type="module" src="/app.js"></script>`。服务端按 MIME 表把这几个文件直出（`.js` 的 MIME 是 `text/javascript; charset=utf-8`），桌面版则把同一份文件交给 Electron 窗口加载。

分工是单向且扁平的：

| 文件 | 职责 |
|---|---|
| `web/app.js`（约 280 行） | 外壳与路由：`NAV` 导航表、`parseHash()`、`VIEWS` 表、`render()`、`paintNav()`、`paintFoot()`、`wireDesktop()` |
| `web/views.js`（约 1630 行） | 各页视图，每个导出 `{ title, desc, async render(ctx) → { html, mount? } }` |
| `web/api.js`（约 250 行） | 接口封装与可复用片段：`h`／`attr`／`toast`／`modal`／`debounce`、`liuyaoHtml`／`hexRowHtml`／`tiyongHtml`／`readingHtml`／`calendarHtml`、时间格式化 |
| `web/palette.js`（约 240 行） | 命令面板：模糊匹配 `fuzzyScore()`、条目构建与键盘交互 |
| `web/chart.js`（约 210 行） | 手写 SVG 多线叠加图表与 `legendHtml` |
| `web/md.js`（约 130 行） | 极简 Markdown 渲染 |
| `web/style.css` | 全部样式（约 920 行），顶部两套主题令牌，之下无一处硬编码色值，无预处理器 |

页面渲染的约定是「返回 HTML 字符串 + 可选的 `mount(root)` 绑事件」，`ctx` 提供 `params`／`meta`／`navigate()`／`reload()`。加一个界面页的动作被写进 `AGENTS.md` 的扩展点速查：`web/views.js` 加视图 ＋ `web/app.js` 的 `NAV`／`VIEWS`／`parseHash`——**无构建步骤，原生 ES 模块**。

零构建也带来了一套独特的验证办法：`tools/check-web.mjs`（123 项）用一个「万能 `Proxy`」充当 DOM，把 `web/app.js` 真正跑起来，逐条路由调用真实的 `render()`，检查每一页该有的东西在不在、有没有 `undefined`／`NaN`／`[object Object]` 漏出来。`tools/check-desktop.mjs`（55 项）则在**真实的 Electron 窗口**里逐页跳转并断言。

## 决策

界面**必须**是浏览器直接可执行的原生 ES 模块，**不得**引入打包器、转译器、CSS 预处理器或前端框架。新增页面**必须**沿用 `{ html, mount? }` 的视图约定，并同时登记进 `web/app.js` 的 `NAV`／`VIEWS`／`parseHash`。样式**必须**写在 `web/style.css`。**不得**为了使用某个前端库而引入构建步骤；需要新交互时**应当**扩 `web/api.js`／`web/chart.js`。

## 理由

1. **可读。** 用户打开 `web/views.js` 看到的就是浏览器实际执行的那份代码，没有编译产物这一层。调试时在开发者工具里看到的行号就是源码行号。
2. **可改。** 改一个标签、调一处文案、加一个按钮，只需编辑文件再刷新。桌面版据此可以做到「改完刷新即可」；命令行版更直接——服务是静态直出，改完即生效。
3. **十年后还能开。** 构建工具链是前端生态里换代最快的一环：今天的打包器配置在几年后往往连安装都困难（旧 Node 版本、废弃的插件、锁定的二进制依赖）。原生 ES 模块是浏览器标准的一部分，随浏览器长期存在。脚本里只用了 `type="module"`、`fetch`、`localStorage`、SVG、`Proxy`（仅自检）这些标准能力。
4. **与零依赖一致。** 前端依赖树通常是整个项目里最庞大、最易被投毒的一环。不做构建，就没有 `node_modules`、没有 lockfile、没有供应链面——与 [ADR-0001](./ADR-0001-零第三方依赖.md) 同源。
5. **体量本来就小。** 十个源文件（`index.html`、`style.css` 与 8 个 `.js`）、约 3400 行，拆分已经足够清晰，不需要打包器做代码分割或摇树。图表是手写 SVG，Markdown 是手写渲染，都不需要编译期优化。
6. **同一份界面同时服务三种形态。** 命令行版（浏览器访问 `127.0.0.1:19730`）、桌面窗口兜底（系统 Edge 以 `--app` 模式打开）、Electron 桌面版，加载的都是这一套文件；若中间插入一层构建产物，三者就要各自维护产物路径与缓存策略。

## 后果

### 正面

- 零安装、零构建、零产物目录：刷新即生效，`view-source` 与源码一致。
- 自检可以绕过浏览器直接跑：`tools/check-web.mjs` 的万能 Proxy 能捕获 `undefined`／`NaN`／`[object Object]` 这类渲染泄漏，成本远低于搭一套前端测试框架。
- 桌面版与网页版共享同一套界面代码，`check-web.mjs` 验过的路由在桌面窗口里同样成立。
- 上手门槛低：会用 `<script type="module">` 与 `fetch` 就能改界面。
- 静态直出没有产物缓存问题：`mainWindow.webContents.reloadIgnoringCache()` 与菜单里的「强制重载」都能立刻看到改动。

### 负面

- **没有类型检查。** 全部是 `.js`，字段拼错、`record.chart.ben` 写成 `record.chart.Ben` 这类问题只能在运行时暴露。部分靠校验器（`schema/record.schema.json` 的 `additionalProperties: false`）与自检的字符串断言（有没有 `undefined`／`[object Object]`）补上，但补不全。
- **没有打包优化。** 首次加载要发 11 个请求（HTML、CSS、图标与 8 个 JS 模块），没有代码分割、没有压缩、没有摇树。对本地回环访问与内嵌窗口来说这些开销可忽略，但它确实是「不做构建」的直接代价。
- **模块数一多就难管。** 目前 `views.js` 已经约 1630 行。若继续加页面而不拆分，单文件会越来越大；而原生 ES 模块的拆分需要手工维护 import 与 `VIEWS` 表，没有构建器替你解析。按现有约定，下一步应当是继续在 `web/` 下按功能拆文件，而不是引入打包器。
- **浏览器兼容靠自觉。** 没有转译就没有降级：用了较新的语法，旧内核会直接报错。当前项目的形态（系统 Edge／Chrome、Electron 自带 Chromium）使这一风险可控。
- **`parseHash()` 是手写路由。** 每加一条路由（如 `#/record/:id`、`#/plugin/:pid/:pageId`）都要在 `parseHash()`、`VIEWS`、`NAV` 三处登记，漏一处就会出现「页面存在但跳不过去」。
- **无构建也意味着无编译期约束。** 视图返回值约定（`{ html, mount? }`）靠人遵守，`app.js` 只做 `out.html || ''` 与 `await out.mount?.(root)` 的宽松处理；写错的视图可能静默渲染为空。

## 备选方案与为何不选

| 方案 | 为什么没选 |
|---|---|
| Vite／Webpack 打包 + 压缩 | 引入整套 Node 工具链与依赖树，与零依赖冲突；且产物与源码分离，破坏「改完刷新即可」这一桌面版的开发体验。 |
| TypeScript 编译到 JS | 编译期类型收益明确，代价是多一层构建与一套类型定义维护，而本项目的数据结构契约已经由 JSON Schema 承担（`schema/record.schema.json`、`schema/gua-tiao.schema.json`）。 |
| 引入前端框架（React／Vue 等） | 体量与依赖都不成比例。现有视图是「拼 HTML 字符串 + mount 绑事件」，页面数量在十个量级，框架带来的状态管理收益很小。 |
| 用 Web Components 替代视图对象 | 会改写整套渲染约定，收益是封装性；当前 `{ html, mount? }` 已足够，且更容易被自检的 Proxy DOM 驱动。 |
| 只做服务端渲染（每页一个 HTML） | 会失去单页的即时切换与前端状态（筛选、勾选、悬停），且要把 `web/views.js` 拆到服务端，等于放弃现有的共享形态。 |
| 引入 CSS 预处理器 | 样式量约 920 行，变量用原生 CSS 自定义属性即可（宣纸／夜读两套主题就是两组令牌）；预处理器只增加构建环节。 |
