# ADR-0010：吉凶评分用加权归一而非简单加减

| 项 | 内容 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-10-03 |
| 决策者 | 项目维护者 |
| 影响的模块 | `core/divination.mjs`（`scoreChart`／`gradeOf`）、`core/verdict.mjs`、`core/trend.mjs`、`core/bagua.mjs`、`knowledge/64gua.json`、`web/api.js`、`data/records/` |

## 背景

吉凶评分在 `core/divination.mjs` 的 `scoreChart()` 里，对八项分别取「归一值 ∈ [−1, 1]」，再按权重求加权平均，最后乘 100 得 −100 ~ +100 的总分：

| 项 | 权重 | 归一方式 |
|---|---|---|
| 体用生克（本卦） | 3.0 | `relation.grade / 3`（grade 取 −3…+3） |
| 变卦结局（对体） | 2.2 | `bianRelation.grade / 3` |
| 互卦中途（对体） | 1.0 | `huRelation.grade / 3` |
| 体卦旺衰 | 1.4 | `WANG[wangTi.state] / 2`（旺2 相1 休0 囚−1 死−2） |
| 用卦旺衰 | 0.6 | **取负**后 `-(WANG[wangYong.state]) / 2` |
| 本卦卦德 | 3.2 | `FORTUNE[ben.fortune] / 4`（大吉4 吉2 中吉1 平0 小凶−2 凶−4） |
| 变卦卦德 | 2.2 | `FORTUNE[bian.fortune] / 4` |
| 动爻得位 | 1.0 | `POS[moving.position] / 2`（1:0 2:+1 3:−0.5 4:−0.5 5:+1 6:0） |

总权重是 3.0 + 2.2 + 1.0 + 1.4 + 0.6 + 3.2 + 2.2 + 1.0 = **14.6**。计算式是：

```js
const totalW = items.reduce((s, i) => s + i.w, 0);
const sum = items.reduce((s, i) => s + i.w * i.v, 0);
const pct = Math.round((sum / totalW) * 1000) / 10;
```

等级由 `gradeOf(pct)` 分档：大吉 ≥55、吉 25~54、中吉 0~24、平 −8~−1、小凶 −40~−9、凶 <−40。界面上「吉凶权衡」把每一项的权重、归一值与说明都摊开显示，README 明写「不服可以改 `core/divination.mjs` 的 `scoreChart`」。

这八项的量纲本来完全不同：生克是有向的五值关系（含方向），旺衰是五行在月令下的五种状态，卦德是卦典里标注的六档吉凶，动爻得位是一个与吉凶方向并不一致的「位置评价」（第二爻与第五爻得中为吉，第三、四爻多惧为不利，初爻与上爻为 0）。**简单加减会把它们当成同一种单位**：用卦旺衰高意味着「事情本身当令」，对问卦人是不利的（所以那一项要取负）；而体卦旺衰高是「我当令」，是有利的。这类方向差异在加减法里无法表达。

权重是校准出来的，校准目标写在代码注释里：「使『体克用而结局受制、卦德又不吉』（如归妹）落于小凶，而『体克用、结局来生、卦德亦吉』（如革之变既济）落于中吉。」

## 决策

吉凶评分**必须**采用「各项先归一到同一量程（[−1, 1]），再按权重加权平均，最后放大到 −100 ~ +100」的方式。**不得**改为各项加权求和的简单加减，**不得**把量纲不同的项直接相加。每一项的**权重、归一值与文字说明必须**随卦录一起存进 `chart.score.breakdown` 并对用户可见。`core/trend.mjs` 的**各领域也必须**先归一到同一量程（除五行占比为 0~100% 单独成模式），**不得**把量程不同的线画在同一根轴上。

## 理由

1. **量纲不同，必须先归一。** 生克是有向关系值，旺衰是五行状态，卦德是六档吉凶标注，得位是爻位评价。它们只有在各自归一之后才具备「可比」的意义；权重表达的是「这件事在整体判断里占多大分量」，而不是「它的原始单位是多少」。
2. **可以举出真实的例子证明简单加减会得出相反结论。**
   - **泽火革**（`data/records/202609280312-01.json`，首占，2026-09-28 03:12 兰州，报数 82，动第四爻）：体卦离火、用卦兑金，体克用（+3）；变卦水火既济对体为**用克体**（−3）；互卦天风姤对体为体克用（+1）；体火于酉月为「囚」（−1）；用金于酉月为「旺」（对体不利，取负后为 −2）；本卦卦德「吉」（+2）、变卦卦德「吉」（+2）；动爻九四为「外卦之始，近君多惧」（−0.5）。**加权归一后**：`[3×1 + 2.2×(−1) + 1×(1/3) + 1.4×(−0.5) + 0.6×(−1) + 3.2×0.5 + 2.2×0.5 + 1×(−0.25)] / 14.6 = 0.282 / 14.6 ≈ +1.9`，落**中吉**（0~24）。`reading` 的「断」写的是「可成而须力，得之在勤，失之在怠」——掌权但费劲，与各项结构吻合。若简单相加：体克用 +3、变卦结局 −3、互卦中途 +1、体卦旺衰 −1、用卦旺衰（取负后）−2、本卦卦德 +2、变卦卦德 +2、动爻得位 −0.5，合计 **+1.5**——数值上看不出问题，但它掩盖了「用金当令、结局受制」这两处强负项，且没有任何机制保证修正这一项（权重 3.0 的体用生克与权重 3.2 的本卦卦德）不被一堆小项淹没。
   - **雷泽归妹**（`data/records/202609280350-01.json`，对照之占「完全不投递只考研」，2026-09-28 03:50 兰州，报数 52，动上六）：体卦兑金、用卦震木，同样是**体克用**（+3）；变卦火泽睽对体为**用克体**（−3）；互卦水火既济对体为体生用（−1）；体金于酉月为「旺」（+2）；用木于酉月为「死」（取负后 +2）；本卦卦德「小凶」（−2）、变卦卦德「小凶」（−2）；动爻上六「事之终，处穷而变」（0）。**加权归一后**：`[3×1 + 2.2×(−1) + 1×(−1/3) + 1.4×1 + 0.6×1 + 3.2×(−0.5) + 2.2×(−0.5) + 1×0] / 14.6 = −2.234 / 14.6 ≈ −15.3`，落**小凶**（−40~−9）。这正是校准目标点：体虽当令、事虽可制，但两卦之德皆偏小凶、结局又受外压，整体判为小凶。若简单相加：`+3 − 3 − 1 + 2 + 2 − 2 − 2 + 0 = −1`，勉强算「平」，与 README 所述「孤注之险」的判定不符。
3. **权重是可校准、可追溯、可回归的。** 权重写在代码里，改动即生效；改完之后可以用六条真实卦录回归比对（`tools/check.mjs` 会核对这六条的卦象与记录是否一致）。界面上逐项展示权重与归一值，用户不服可以照自己的意思改。
4. **归一让走势可以叠看。** `core/trend.mjs` 的六个吉凶领域（`score`、`relation`、`bian`、`tiWang`、`grade`、`tiYangRatio`）全部归一到 −100 ~ +100，因此能画在同一张图里比较：同向＝彼此印证，背离＝卦气与结论有张力。五行占比是 0~100% 量程，单独成模式，`SCALE` 常量把它与 `signed` 明确分开。

## 后果

### 正面

- 八项各有分工、各有分量，最终分数可以被拆开解释；每一处扣分加分都能指到具体项与具体说明。
- 权重与等级的对应关系经得起回归：六条历史卦录的总分与等级可由 `cast(record.cast)` 精确重算，结果与存档完全一致（泽火革 +1.9 中吉、天山遁 +38.8 吉、泽雷随 −30 小凶、泽风大过 +28 吉、天泽履 +46.7 吉、雷泽归妹 −15.3 小凶）。
- 等级分档有明确的语义描述（`gradeOf` 的 `desc`），不是只有一个数字。
- 走势图能在一张轴上做多线对照，这是「多领域叠加」这个产品卖点的技术前提。
- 权重与词库是同一个扩展点：改 `core/divination.mjs` 的 `scoreChart` 就能调口径，旧卦录不受影响，需要时显式重算。

### 负面

- **权重的取值本质上是经验值。** 3.0、2.2、3.2、1.4、0.6、1.0 这些数字来自校准目标而不是可观测量。换一个校准目标（例如强调结局重于过程）就要重调一遍，且没有客观标准能证明某组权重更「对」。
- **归一压掉了绝对值的信息。** 归一之后的 −1 与 +1 是「该项的最不利／最有利」而不是「差多少量」。因此总分是相对评价，不能解释为概率或期望。
- **八项之间存在相关性，权重会重复计。** 变卦对体的生克与变卦卦德都从变卦来，本卦卦德与互卦、体用生克也可能同向，因此总分对同一件事实的敏感度高于单项权重所暗示的程度。
- **用卦旺衰取负是一个约定。** 它的依据是「事情本身当令则我受制」，但在体用比和或体生用等关系下这条解释并不总是成立；`scoreChart` 把它固定为取负，属于简化。
- **改动权重会改变历史可比性。** 旧卦录存的是快照，所以旧分数不会变；但同一批卦里新旧分数并存时，走势图上的「总评分」线会跨越口径变化——`core/trend.mjs` 不做口径标注，用户需要自己记得哪一卦之后调过权重。

## 备选方案与为何不选

| 方案 | 为什么没选 |
|---|---|
| 简单加减（各项给整数分，直接求和） | 量纲不同、方向不同（用卦旺衰要取负），加总结果依赖各项取值范围的人为设定；上文对泽火革与雷泽归妹的演算表明它会掩盖强负项、把结论推向乐观一侧。 |
| 只用体用生克一项定吉凶 | 会丢掉月令旺衰、卦德、动爻这些梅花易数里本来就参与判断的信息；`reading` 的「主」段明写「体用为骨、月令为气、卦德为肉、动爻为应」，四者都要有分量。 |
| 让 LLM 综合判断给分 | 不可复现、不可回归，违反 [ADR-0003](./ADR-0003-断语用规则引擎.md)。 |
| 用「等级」而不是连续分数 | 等级更稳但太粗：中吉与吉之间的差别、同一等级内的轻重都表达不出来，走势图也失去分辨率。当前做法是连续分数加等级分档，两者都提供。 |
| 权重做成用户可调的配置项 | 会让「同一条卦录在不同配置下得到不同分数」成为常态，历史可比性彻底消失。当前做法是把权重固定在代码里、界面只读展示，要改就得改代码——这是一次有意识的成本交换。 |
| 归一后改用几何平均／最小值决定法 | 几何平均对负值无定义（本项目分数可正可负）；最小值法会让任何一个极端项主导结论，与「八项加权」的初衷相反。 |
