# ADR-0011：校勘存而不改

| 项 | 内容 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-10-03 |
| 决策者 | 项目维护者 |
| 影响的模块 | `core/record.mjs`（`audit`／`buildRecord`／`recompute`）、`core/guaTiao.mjs`、`core/importer.mjs`、`core/migrate.mjs`、`server/store.mjs`、`schema/record.schema.json`、`web/views.js`、`tools/seed.mjs`、`data/records/` |

## 背景

导入旧卦时，程序会把自己**按正法重算**的结果与「当初所述的卦」逐项对照，不同处列进 `corrections`。字段分工是：

| 字段 | 存什么 |
|---|---|
| `claimed` | 当初别人是怎么说的：`ben`／`hu`／`bian`／`moving`／`tiyong` |
| `corrections[]` | 它与重算结果的差异，每条含 `field`、`label`、`stated`、`computed`、`note` |
| `narrative` | 当初的**完整原文**，整段保留 |

`core/record.mjs` 的 `audit(claimed, chart)` 逐项比对：卦名用 `library().find()` 归一（`泽水困`／`困`／`47`／`䷮` 都认），认不出的**不报**——注释写着「以卦典为准比对卦名：认不出的不报，避免误伤」；动爻不同则记 `moving`；体用用正则从原述里抠出「体卦X／用卦Y」比对校勘（见 `core/record.mjs` 的 `audit()` 里 `statedTi`／`statedYong` 两处匹配）。

每条 `note` 都要说清「为什么不同」，而不是只报一个差异：

- 互卦：`互卦取「二三四爻为下、三四五爻为上」，此处原述有误，已按正法改正。`
- 变卦：`变卦由动爻反覆而得，此处原述有误，已按正法改正。`
- 动爻：`动爻取法不同（有「数与时之和除六」与「仅以报数除六」两说），此处已按所记取法还原。`
- 体用：`体用之法定「动爻所在之卦为用，另一卦为体」；此处原述与正法不同，已按正法改正（若两卦同五行，吉凶结论不受影响）。`

界面上「校勘」卡片把每条渲染成「原述「…」→ 正法「…」」加一句说明，卡片下的提示是：「以下为当初口头解读与本程序依正法重算之差异——**一并存录，不作删改**。」

已有六条历史卦录里真实照出两处：**天泽履**（考研主线之占）当初写「体卦兑金，用卦乾金」，按正法则「动爻在下卦，故下卦兑为用、上卦乾为体」，应为体乾、用兑（两卦同属金，体用比和的结论不受影响）；**雷泽归妹**（完全不投递之占）当初写互卦为「山火贲」，按正法应为**水火既济**。

另外还有两类**取法存异**（不是错，是当初用了另一路取法），由 `tools/seed.mjs` 的 `extraCorrections` 写入：

- 首占**泽火革**的动爻，当初以 `82 ÷ 6` 单独取（得第四爻「改命吉」）；梅花易数常法为「数与时之和除六」（得初爻）。卦录**按原卦保留第四爻**，并在校勘里注明若改常法重算会得到什么。
- 两个**对照卦**（泽雷随／泽风大过）当初用的是「下卦取『数与时之和除八』」的另一路取法。卦录用「已知卦象」（`method: 'manual'`）模式**忠实保留原卦**。

与「存而不改」配套的还有两条更广的规矩，写在 `AGENTS.md` 的硬规矩里：迁移必须**先备份到 `data/backups/pre-migration/`** 再落盘；删除只允许移入 `data/trash/`，`?hard=1` 才真删且只应由用户主动触发。`core/migrate.mjs` 对缺迁移函数与迁移抛错的处理也是「按原样载入并告警，不会丢数据」。

## 决策

导入旧卦时，**必须**把「当初所述」原样存进 `claimed`，把与重算的差异存进 `corrections`，并**必须**把当初的完整原文保留在 `narrative`。**不得**删改、覆写或「顺手修正」用户的原文；**不得**因为重算结果与所述不同就丢弃所述一侧。当差异源于另一路起卦／取动爻之法时，**应当**优先忠实保留原卦（用 `method: 'manual'` 或 `inferMovingFrom()` 反推取法），把差异作为「取法存异」记入校勘，而不是把原卦改成本程序的默认算法结果。校勘**必须**写明差异原因（`note`），**不得**只列差异不解释。

## 理由

1. **原文是唯一的不可再生资料。** 卦辞、爻辞可以查书，卦象可以重算，但「当初那个人是怎么说的、用户当时读到的是什么」只有一份。一旦覆写，用户就再也无法判断自己当初的决策依据是什么。
2. **用户可能记得的是原述，不是重算结果。** 用户回看卦录时，脑中往往是当年读到的那句「体卦兑金」。若程序把原述删掉、只留改正后的结论，用户会觉得记录与记忆不符，却查不到原因。两侧并存才能解释这种不一致。
3. **「错」与「另一路取法」必须分开。** 互卦取法写错、体用定错，属于笔误，重算一侧是对的；而「动爻以报数单独取」是梅花易数中确有的一路取法（`movingFrom: 'number'`），只是与常法不同。把它当作「错」来改，就等于把用户的真实卦象改掉——那才是真正的数据损坏。所以卦条解析与 `buildRecord()` 里都有反推逻辑：所述动爻只与某一路吻合时按那一路还原。这个逻辑曾被默认值挡住，导致误报校勘，被 `tools/check.mjs` 抓出并修掉。
4. **金句「若两卦同五行，吉凶结论不受影响」是必要的一句。** 体用定反在天泽履那条里并不改变「体用比和」的吉凶判断，若只报「体用写错了」而不说明结论不变，用户会以为整条卦录作废。
5. **同一原则贯穿数据全生命周期。** 迁移先备份、删除先进回收、重算只替换快照——三条规矩与「校勘存而不改」是同一条价值观的不同侧面：**程序可以给出更好的结果，但不可以替用户抹掉历史。**

## 后果

### 正面

- 卦录是「可对话的历史」：原文、原述、重算结果三者都在，能回答「当初为什么这么判、现在为什么不一样」。
- 校勘本身成为价值：六条历史卦录照出两处错误与两类取法存异，这是本项目相对聊天记录最实在的一处增值。
- 数据损坏面被压到最小：迁移失败按原样载入，删除先进 `trash/`，原文段永不被程序重写。
- 校勘可被统计与筛选：`Store.stats()` 给出 `corrections` 计数（总览页显示「含校勘」），`summarize()` 给列表带 `correctionCount`。
- 取法反推让「别人给的卦」能被忠实录入——同时更新 `docs/规范.md` 与 `core/guaTiao.mjs` 时都要照顾这条路径（`AGENTS.md` 的扩展点速查专门提醒过）。

### 负面

- **界面与导出的体量增加。** 详情页多一块校勘卡片，导出里也有校勘段；对没有校勘的卦录这些位置为空，属于可接受的噪音。
- **校勘的判定依赖卦典能认出卦名。** `audit()` 对认不出的原述选择「不报」，因此用户若把卦名写成了错别字，校勘**不会**提醒，而是静默跳过。这是为了避免误伤而接受的漏报。
- **体用比对是正则匹配。** 只能识别「体卦X／用卦Y」这种写法；若原述写成「我克彼」之类的自然语言，就比对不出来。
- **校勘会随重算更新，因此不是历史快照。** 重算时 `corrections: audit(record.claimed, chart)` 会按新 `chart` 重算，若引擎改了互卦算法，校勘条目本身会变。校勘记录的是「原述 vs 当前正法」，不是「原述 vs 当年的正法」——这一点需要使用者理解。
- **取法反推有边界。** 两路取法算出同一个动爻时从常法（注释：「两者都能得到同一个动爻时，从常法」）；两路都对不上时返回 `'sum'`，差异留给校勘。这两种情况都不会被特别标注出来，用户需要读 `casting.steps` 才知道实际用了哪一路。

## 备选方案与为何不选

| 方案 | 为什么没选 |
|---|---|
| 以重算结果为准，直接覆盖所述 | 会永久丢失原述与原文；用户无法再核对「当初读到的是什么」，校勘本身也无从谈起。 |
| 以所述为准，不重算也不校勘 | 等于放弃引擎的正确性；互卦取法写错这类错误会被永久保留并继续误导后续判断。 |
| 只在校勘里报差异，但把 `narrative` 里的原句一并替换成正确表述 | 那是最坏的一种：既改了原文，又让用户以为原文本来如此。 |
| 把校勘写进 `review.log` 或单独的 `audit.json` | 会脱离卦录本体，备份、导出、迁移都要额外照顾；`corrections` 放在记录里，随记录一起走。 |
| 用 `fidelity` 一类字段标注「本条记录的可信度」 | 与 `claimed`／`corrections` 表达同一件事但更含糊，且会给用户一个「这条不可信」的整体印象，而实际差异可能只影响一个不影响结论的字段（如天泽履的体用）。逐项列差异更精确。 |
