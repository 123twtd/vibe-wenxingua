# 问心卦 · 数据格式与导入规范

> 版本：卦条 v1　/　卦录 JSON schema v3
> 本文是**规范**（normative）：写导入、写脚本、让 AI 替你录卦，都照这个来。
> 想改规范，请连同 `schema/*.json`、`core/migrate.mjs`、`tools/validate.mjs` 一起改，并在文末「版本历史」记一笔。

---

## 一、为什么要有这份规范

之前的问题是：卦录 JSON 完整但难手写；DeepSeek 的对话文本好粘但没标准。于是「以后新导入怎么办」没有答案。

现在有三个入口，**共用同一套解析器**，所以行为一致：

| 入口 | 用法 |
|---|---|
| 网页 | 「导入与格式」页粘贴 → 解析 → 复核 → 入库；同一页的粘贴框就是在线校验 |
| 命令行 | `node tools/import.mjs 卦条.txt` |
| AI / 外部 agent | agent 工具 `save_gua_tiao`（HTTP 或 MCP 都行） |

校验一律用 `node tools/validate.mjs` 或 `POST /api/validate`。

## 二、卦条 v1（人写的导入格式）

### 2.1 长什么样

```
# 卦条 v1
题: 换城之占
问: 换一座城市重新开始，可行吗？
类: 决策取舍
时: 2026-10-05 05:20
地: 上海
经: 121.47
真太阳时: 是
法: 一数一时辰
数: 63
动: 4
背景: |
  求测人在上海，换城之意起于三月，主业求稳、副业次之。
原文: |
  这是一段可以多行的原文。
  想放多少放多少。
方案: |
  先落地再谋变：入秋前不动现职，只做两件准备。
校勘: |
  「第四爻阳变阴」应作「六四阴爻动，变阳」。
```

一行一个字段，`键: 值`。键可用中文全称或简写。首行 `# 卦条 v1` 可以省（省了也能认）。**多条卦条用单独一行 `---` 分隔。**

末四种（`背景`／`方案`／`校勘`／`问答`）与 `原文` 一样，写 `键: |` 起一个**多行块**，缩进不限、内容原样保留、不做解析。它们都是**可省**的——不写就不进卦录。

### 2.2 字段字典

| 内部字段 | 可写的键名（任选其一） | 必填 | 说明 |
|---|---|---|---|
| `title` | 题 / 标题 / title | 否 | 留空则由「问」自动截取 |
| `question` | 问 / 所问 / 所问之事 / 问题 / question | 否 | 一事一占；写得越单一，卦象越不散 |
| `category` | 类 / 类别 / category | 否 | 见 §4.1；留空则按「问」自动归类 |
| `tags` | 标签 / tags | 否 | 空格或逗号分隔 |
| `localTime` | 时 / 时间 / 起卦时间 / 钟表时间 / time / localTime | **是** | 钟表时间，格式 `YYYY-MM-DD HH:mm`；`2026.10.5 5:20` 这类也认 |
| `placeName` | 地 / 地点 / 城市 / place | 否 | 留空则用配置里的默认地点 |
| `longitude` | 经 / 经度 / 东经 / longitude / lon | 否 | 填了就以此为准，否则按「地」查表 |
| `latitude` | 纬 / 纬度 / 北纬 / latitude / lat | 否 | 目前只存档，不参与计算 |
| `useTrueSolarTime` | 真太阳时 / 真太阳 / trueSolar | 否 | 是／否；默认「是」。**这一项会改变时辰，从而改变整个卦** |
| `method` | 法 / 起卦法 / 方法 / method | 否 | 见 §2.3；留空则按所给信息推断并给出提示 |
| `numbers` | 数 / 报数 / 数字 / numbers | 视 `法` | 一数写一个；两数写 `617 15` |
| `movingFrom` | 动爻取法 | 否 | `sum`（数与时之和除六，常法，默认）或「仅报数」 |
| `hexagram` | 本卦 / 卦 / hexagram / ben | 视 `法` | `法` 为「已知卦象」时必填。`泽水困` / `困` / `47` / `䷮` 都认 |
| `movingPosition` | 动 / 动爻 / moving | **是**（`年月日时` 除外） | 自下而上第几爻，1–6 |
| `hu` / `bian` | 互卦 / 变卦 | 否 | 写了就与重算结果对校，不符则记入**校勘** |
| `tiyong` | 体用 | 否 | 同上，写如 `体乾金，用兑金，体用比和` |
| `signature` | 签 / 谶 / signature | 否 | 写了就覆盖引擎生成的谶语 |
| `narrative` | 原文 / 原记录 / 记录 / narrative | 否 | 用 `原文: \|` 起一个多行块。放**解读全文** |
| `background` | 背景 / 求测人背景 / 背景动机 / background | 否 | 用 `背景: \|` 起多行块。求测人背景：身份、处境、动机，几件事各占几分 |
| `plan` | 方案 / 可执行方案 / 行动方案 / plan | 否 | 用 `方案: \|` 起多行块。可执行方案：断语给的是通则，这里存落到这件事上的具体做法 |
| `collation` | 校勘 / 人工校勘 / 勘误 / collation | 否 | 用 `校勘: \|` 起多行块。**人工**校勘：人对旧解读措辞的更正。与程序自动算出的校勘（`corrections`）分开 |
| `qa` | 问答 / 原文问答 / 问答原文 / qa | 否 | 用 `问答: \|` 起多行块。原文问答，约定以「问：」「答：」起行 |
| `status` | 复盘 / 状态 / status | 否 | 见 §4.2；默认「待应验」 |
| `result` | 实况 / 结果 / result | 否 | 复盘实况 |

### 2.3 `法` 的取值

| 中文名 | 内部 id | 需要 | 说明 |
|---|---|---|---|
| 一数一时辰 | `numberAndTime` | 数 + 时 + 动 | 上卦取数除八，下卦取时辰数除八，动爻取二者之和除六 |
| 两数 | `twoNumbers` | 数(2个) + 时 + 动 | 先报数为上卦，后报数为下卦，两数之和除六取动爻 |
| 年月日时 | `timeOnly` | 时 | 年支＋月＋日为上卦，再加时辰为下卦，总和除六取动爻；**动爻可省**（会算出来） |
| 已知卦象 | `manual` | 本卦 + 动 | 用于录入别人替你起的卦；互卦、变卦、体用由本程序算 |

### 2.4 必填与「不许猜」

- 时（起卦时间）必填。
- `法` 为「已知卦象」时：须填 `本卦` 与 `动`。
- 其余起卦法：须填 `数` 与 `动`（`年月日时` 免 `动`）。

**缺什么就报什么。** 解析器宁可返回「缺：起卦时间」，也不会替你猜一个年份。识别结果的 `missing` 数组列出缺项，`unknownKeys` 列出认不出的键名（多半是写错了字）。

### 2.5 完整示例（两条）

```
# 卦条 v1
问: 我以备考河北工业大学研究生为唯一主线，正常完成课程设计，仅少量精投几家保底。能否上岸？
类: 考研学业
时: 2026-09-28 03:38
地: 兰州
真太阳时: 是
法: 一数一时辰
数: 1
动: 3
本卦: 天泽履
互卦: 风火家人
变卦: 乾为天
体用: 体乾金，用兑金，体用比和
签: 两情既叶，事无龃龉。守其常道，久而有成。
背景: |
  唯一主线是备考，课程设计按常规完成即可，保底只投少量。
问答: |
  问：还要不要额外投几家？
  答：主线既定，投得多反分心；只留少量保底即可。
原文: |

---
# 卦条 v1

时: 2026-09-30 22:10
地: 兰州
法: 已知卦象
本卦: 泽水困
动: 4
```

## 三、卦录 JSON（程序存的东西）

一条卦录一个文件，落在 `data/records/<id>.json`。id 形如 `202609280338-01`（起卦时间 `YYYYMMDDHHmm` ＋ 两位序号），一经生成不再更改。

### 3.1 三个关键字段的分工

| 字段 | 角色 | 规矩 |
|---|---|---|
| `cast` | **唯一真源** | 起卦输入。任何一条卦录都能由它重算，所以它必须完整、可读、不省略 |
| `chart` | 卦局快照 | 本卦／互卦／变卦／六爻／动爻／体用／旺衰／评分／历法。**引擎升级后旧快照不动** |
| `reading` | 断语快照 | 谶 ＋ 七段定调 ＋ 通俗解 ＋ 古辞佐证。同上 |

这样设计的理由：断语引擎一定会改，但**你已经存下的卦不能因为引擎改了而变样**。想用新引擎看旧卦，点卦录详情页的「重算断语」，那是一次显式操作。

### 3.2 根级必填

`schema`、`id`、`title`、`category`、`cast`、`chart`、`reading`、`review`、`createdAt`、`updatedAt`。

其余字段（`question`／`claimed`／`corrections`／`narrative`／`background`／`plan`／`collation`／`qa`／`tags`／`origin`／`revisionCount` …）的完整定义见 **[schema/record.schema.json](../schema/record.schema.json)**。根级 `additionalProperties: false`——写错字段名会被校验器抓出来。

### 3.3 校勘

`claimed` 存「当初别人是怎么说的」，`corrections` 存它与重算结果的差异。**一律存录，不删改原述。**

```jsonc
"claimed": { "ben": "天泽履", "tiyong": "体卦兑金，用卦乾金，体用比和" },
"corrections": [{
  "field": "tiyong", "label": "体用",
  "stated": "体卦兑金，用卦乾金，体用比和",
  "computed": "体乾金（上卦）、用兑金（下卦），体用比和",
  "note": "体用之法定「动爻所在之卦为用，另一卦为体」…"
}]
```

**两种校勘要分清：**

| | 字段 | 谁写的 | 内容 |
|---|---|---|---|
| 自动校勘 | `claimed` ＋ `corrections` | 程序 | 卦条里写了本卦／互卦／变卦／动爻／体用，程序重算后逐项对校，不符就记一条 |
| 人工校勘 | `collation` | 人 | 程序算不出来的措辞更正。如「第四爻阳变阴」应作「六四阴爻动，变阳，艮变离」 |

自动校勘是**结构化的差异**，机器可读；人工校勘是**一段话**，给人看。两者分开存，互不覆盖——不要把人写的东西塞进 `corrections`，那会让「这条差异是程序算出来的」这个前提失效。

### 3.4 补充存录

除 `narrative`（解读全文）外，还有三项也是**人带来的、程序永不改写**的自由文本，用来补足「完整占问」里引擎算不出的东西：

| 字段 | 卦条键 | 记什么 |
|---|---|---|
| `background` | 背景 | 求测人的身份、处境、动机，几件事各占几分 |
| `plan` | 方案 | 可执行方案：断语给的是通则，这里存落到这件事上的具体做法 |
| `qa` | 问答 | 原文问答，约定以「问：」「答：」起行 |

四项都可省，默认空串。它们与 `reading`（程序算出的断语快照）是两回事：**断语会随引擎升级而重算，这四项不会。**

## 四、枚举值

### 4.1 类别 `category`

`考研学业`｜`求职事业`｜`财运生计`｜`心态情绪`｜`作息健康`｜`人际情感`｜`决策取舍`｜`其他`

类别决定断语里「宜／忌」的取向。留空时按「问」里的关键词自动归类（如含「考研／初试／复试」→ 考研学业）。

### 4.2 复盘状态 `review.status`

`待应验`｜`应验中`｜`已应验`｜`未应验`｜`已过期`｜`无需应验`

### 4.3 吉凶等级 `reading.grade.label`

`大吉` ≥55｜`吉` 25~54｜`中吉` 0~24｜`平` −8~−1｜`小凶` −40~−9｜`凶` <−40（总评分 −100 ~ +100）

### 4.4 起卦法 `cast.method`

`numberAndTime`｜`twoNumbers`｜`timeOnly`｜`manual`

### 4.5 断言七段的顺序（不可变）

`主` → `互` → `变` → `断` → `宜` → `忌` → `应期`

`tools/validate.mjs` 会验这个顺序。要改顺序就得升 `schema` 版本。

## 五、版本与迁移

### 5.1 机制

- 每条卦录带 `schema` 号，当前为 **2**。
- 载入时若 `schema` 低于当前，按 `core/migrate.mjs` 的 `MIGRATIONS` 登记表**逐级迁移**。
- **迁移前原件自动备份到 `data/backups/pre-migration/<id>-v<旧版本>-<时间戳>.json`**，可回退。
- 迁移函数是纯函数（旧记录 → 新记录），可用 `node tools/validate.mjs` 单独验。
- 缺失迁移函数时，该条按原样载入并告警，**不会丢数据**。
- **迁移只许新增字段，不许改已有字段。** `check.mjs` 有一条断言守着这句：
  把一条 v1 记录迁到 v2，前后比对 `cast`／`chart`／`reading` 必须一字不差。

### 5.2 加一个新版本怎么做

1. `core/migrate.mjs`：`CURRENT_SCHEMA` 加一，`MIGRATIONS[旧版本]` 写转换函数；
2. `schema/record.schema.json` 同步改；
3. 本文「版本历史」记一笔：改了什么、为什么、兼容性影响；
4. 跑 `node tools/validate.mjs` 与 `node tools/check.mjs`。

> 自检里**不要写死版本号**。写死的话每次升版都要来改自检，那正是「第二真源」的毛病。
> `check.mjs` 与 `check-web.mjs` 现在都跟着 `CURRENT_SCHEMA` 走。

### 5.3 版本历史

| 版本 | 变更 | 兼容性 |
|---|---|---|
| **v1** | 初始。`cast`／`chart`／`reading` 三分，`claimed`＋`corrections` 校勘，`review` 复盘 | — |
| **v2** | 新增 `yingqi`（应期区间）。走势图因此能按**应验时间**落点，而非只看起卦时间 | **纯新增**。老记录从 `chart` 现算补上，`reading` 快照一字不动；算不出则留 `null`，不影响载入 |
| **v3** | 新增 `background`／`plan`／`collation`／`qa` 四项**补充存录**（对应卦条键 背景／方案／校勘／问答）。原先卦条只够「重算卦象、核对互变体用」，对「完整占问」不够——背景、可执行方案、原文问答、以及程序算不出的人工校勘都无处安放 | **纯新增**。老记录迁移时四项一律补空串，`cast`／`chart`／`reading`／`claimed`／`corrections` 一字不动；卦条仍是 v1（只新增键别名，不删改旧别名），旧文件永远能读 |

> v3 只动**根级**字段，不动 `claimed`／`corrections` 的语义：人工校勘单独存 `collation`，程序自动算出的差异仍归 `corrections`。两者混源就分不清「哪条是机器算的」了。

### 5.4 应期区间 `yingqi`

| 字段 | 类型 | 说明 |
|---|---|---|
| `minDays` / `maxDays` | 整数 | 区间起止，自起卦之日起算 |
| `from` / `to` | `YYYY-MM-DD` | 对应日期；缺起卦时间时为空串 |
| `horizon` | `near`｜`mid`｜`far`｜`long` | 近期（≤21 天）／中期（≤70）／较远（≤200）／长期 |
| `horizonName` / `unit` / `hint` | 字符串 | 「较远」「以月计」「半年上下，须过一两个节令」 |
| `inSeason` | 布尔 | 体卦是否当令得气 |
| `seasonAt` | 对象｜`null` | 体未得气时，「得令之月」那一段；**量化上限就是它** |
| `basis` | 对象 | 逐项依据：旺衰基准、生克系数、卦数系数、天花板 |
| `reason` | 字符串 | 一段人话说明这个区间怎么来的 |
| `source` | `computed`｜`manual` | 算出来的还是人改的 |

**推算依据**（`core/yingqi.mjs`），与断语里「应期」那一段**同一套规矩**：

1. **动爻之位定时段**——初爻在旬日，上爻逾年；
2. **体气得令则应提前**——旺相则「不至久留」，用提前一档的短窗口；
   休囚死则**须待体卦五行得令之月**（如木待寅卯、火待巳午），那一段就是量化上限；
3. **体用生克定顺逆**——用生体来得快，体生用与用克体都要拖；
4. **卦数**——体用先天数之和越大，事体越重，稍缓。

第 3、4 项是乘性微调，且**受第 2 项的天花板约束**：断语说「须待寅卯月」，
量化结果就不许跑到卯月之后去。`check.mjs` 有一条断言逐条比对这件事。

### 5.5 走势的横轴与领域

`GET /api/trend` 的 `axis` 决定每条卦落在横轴的哪一天：

| `axis` | 落在 | 用途 |
|---|---|---|
| `cast`（默认） | 起卦那天 | 看「我当时都问了什么」 |
| `due` | **应验那天**（`yingqi.to`） | 看长期之事——否则半年后的事和今天的事挤在同一点上 |

同一批卦切到 `axis=due`，跨度会从不足一日拉开到数月。缺 `yingqi` 的卦**退回按起卦时间放，不会被丢掉**，条数记在返回值的 `dueFallback` 里。

`mode=domain` 是**按领域（类别）分别成线**：一个领域一条运势线；同领域起过多卦时，
用**时间衰减加权的累计均值**综合成基准（半衰期 90 天，越近的卦权重越大）。
另加一条虚线「全体基准」作对照。每卦相对本领域基准的**偏离**在 `deviations` 里返回——
偏得越多越值得看。

## 六、走势数据的取用（只读接口）

`GET /api/trend`（或 agent 工具 `trend`）返回多线叠加的时间序列。参数：

| 参数 | 取值 | 说明 |
|---|---|---|
| `mode` | `fortune`｜`domain`｜`element`｜`category` | 吉凶诸线叠加／**领域运势**／五行占比／分类别累计均值 |
| `domains` | `score,relation,bian,tiWang,grade,tiYangRatio` | `mode=fortune` 时选哪些线；`mode=domain` 时取第一个作基准 |
| `axis` | `cast`｜`due` | 横轴落在**起卦那天**还是**应验那天**（见 5.5） |
| `smooth` | 1–12 | 移动平均窗口，1＝不平滑 |
| `rangeDays` | ≥0 | 只取最近 N 天，0＝全部 |
| `categories` | 逗号分隔 | 只看这些类别 |
| `xMode` | `index`｜`time` | 横轴按卦序或按时间比例 |

除五行占比（0~100%）外，各线均归一到 **−100 ~ +100**，因此可叠在同一量程里比较。时间跨度不足一日时时间轴会退化为等距，并在 `notes` 里说明——**不假装是真时间轴**。

## 七、校验

```bash
node tools/validate.mjs                    # 全部卦录
node tools/validate.mjs 我的卦条.txt        # 一个卦条文件（多条会逐条校验）

```

校验范围：schema 结构（含根级未知字段）＋ 语义约定（七段顺序、六爻长度、动爻阴阳与六爻数据一致）。

## 八、兼容性承诺

- 卦条 v1 的**字段名与别名不会删改**，只会新增别名。旧文件永远能读。
  （v3 新增的 `背景`／`方案`／`校勘`／`问答` 就是这一类纯新增别名；卦条版本号因此仍是 v1。）
- 卦录 JSON 只做**向前迁移**，不做破坏性重写；`data/records/` 下的文件永远可以被后来的版本读入。
- 数据是纯文本 JSON，不依赖本程序也能读。程序跑不起来时，你的卦录依然在。
